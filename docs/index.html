Welcome to Settled 👋

Settled is real-time group food ordering: one person starts an order, friends join by link, QR or code, everyone adds their own items to a cart that updates live on every phone, and the host pays once. This playbook is everything you need to go from zero to your first merged pull request.

Maintained by Jordan Goddard (founder · tech lead · Product Owner) · Last updated October 2026 · Questions? Ask in standup or open an issue labeled question.

Your first hour

# 1. Prerequisites: Node 22+, Git, VS Code (see section 2)
git clone https://github.com/jordangoddard6/settled.git
cd settled
npm ci                       # installs deps and the git pre-commit hook
cp .env.example .env         # add Stripe TEST keys (Jordan shares them; see section 9)
npm run dev                  # app at http://localhost:5173, API at :3001
npm run check                # lint + format + typecheck + tests: should all pass

Then open http://localhost:5173 in one browser and the same cart link at http://127.0.0.1:5173 in another: they're separate identities, so you can watch the cart sync between two people on one machine.

1Language selection In use

One language, end to end: TypeScript 6 in strict mode.

Layer What we use Lives in
Front end TypeScript · React 19 · Vite 8 · Tailwind CSS 4 src/client/
Back end TypeScript · Node.js 22 · Express 5 · Socket.IO 4 · Zod (input validation) src/server/
Shared Types, menus, pricing and the socket protocol, imported by both sides src/shared/
Payments Stripe (test mode) via stripe + @stripe/react-stripe-js src/server/payments.ts

Why TypeScript everywhere

  • The real-time contract is typed once. src/shared/protocol.ts defines every Socket.IO event. If the server changes a payload, the client stops compiling: no silent "cart didn't update" bugs.
  • One language, one toolchain. Anyone can work on any layer, and lint/format/test config is shared.
  • First-class ecosystem. React, Socket.IO, Stripe and Zod all ship TypeScript types, and AI coding tools are strongest in TS.
  • Hiring. TypeScript/React is the most common skill set for web startups.
Why TypeScript 6, not 7? TypeScript 7 (the native Go compiler) doesn't expose the JavaScript API that typescript-eslint needs for type-aware linting, so we pin typescript@^6.0.3. We'll upgrade when typescript-eslint supports 7.

2IDE selection & setup Configured in repo

Recommended: Visual Studio Code. Any IDE is allowed: formatting, linting and tests are enforced by the pre-commit hook and CI, not by your editor.

Install

  1. VS Code: code.visualstudio.com/download
  2. Node.js 22 LTS or newer: nodejs.org/en/download (check with node -v)
  3. Git: git-scm.com/downloads

Set up (about 5 minutes)

  1. Clone the repo and run npm ci (see Start here).
  2. Open the folder in VS Code. When prompted "Do you want to install the recommended extensions?", click Install. The list comes from .vscode/extensions.json.
  3. When prompted to use the workspace TypeScript version, click Allow so the editor matches CI.
  4. Sign in to GitHub Copilot and Claude Code (see section 6).
Extension Why
ESLint · Prettier Inline lint errors; format on save; ESLint fixes on save (.vscode/settings.json)
Tailwind CSS IntelliSense Class autocomplete and previews
Vitest · Playwright Test Run and debug individual tests from the editor
Claude Code · GitHub Copilot (+ Chat) Our two approved AI tools

Using another IDE (WebStorm, Zed, etc.)? Turn on its ESLint and Prettier integrations, point it at the workspace TypeScript in node_modules/typescript, and use LF line endings.

3Development strategy Scrum · 1-week sprints

We run Scrum with 1-week sprints. Short sprints keep the "no changes mid-sprint" rule cheap: what we learn from users on Monday can be planned the following Monday.

Roles

Role Who Owns
Product Owner Jordan The backlog and its priority order; sprint goal; accepting work in review
Scrum Master Rotates each sprint among engineers (you take it in your 2nd or 3rd sprint) Runs the meetings, keeps the board honest, removes blockers, protects the sprint
Development Team All engineers (Jordan included) Estimating, building, testing and shipping the sprint's issues

The week

When Meeting Length Output
Monday 9:30 Sprint planning 45 min Sprint goal; issues pulled from To Do into the new Iteration; each estimated in points
Tue–Fri 9:30 Daily standup 15 min Yesterday / today / blockers, walking the board right to left
Thursday 2:00 Backlog grooming 30 min Top of the backlog is "Ready": clear, estimated, has acceptance criteria
Friday 2:00 Sprint review 30 min Demo what shipped (on the live app); PO accepts or returns work
Friday 2:30 Retrospective 30 min One or two process changes, filed as chore issues

Working agreements

  • Estimates use story points (1, 2, 3, 5, 8). Anything bigger than 8 gets split in grooming.
  • Definition of Ready: a user-facing goal, acceptance criteria, an estimate, and no open questions.
  • Definition of Done: merged to main through a reviewed PR, CI green, tests added, deployed to Render, issue closed.
  • No mid-sprint scope changes, except Sev 1/2 production incidents (see on-call). New ideas go to the Backlog for Monday.

4Git strategy & controls Enforced on main

We use GitHub Flow: main is always deployable, and every change goes through a short-lived branch and a pull request. Merging to main deploys to production.

Branch off main→Commit & push→Open PR→CI + 1 review→Squash-merge→Render deploys

Branch names

<type>/<issue#>-<short-description>, where type is feat, fix, chore, docs or test. Examples: feat/14-split-bill, fix/22-checkout-lock. Keep branches short-lived (merge within a sprint) and delete them after merging (GitHub does this automatically). 

git switch main && git pull
git switch -c feat/14-split-bill
# ...work, commit (the pre-commit hook lints and formats staged files)...
git push -u origin feat/14-split-bill
gh pr create --fill          # or open the PR on GitHub; fill in the template

Commit messages (guideline)

  • Imperative subject, 72 characters or fewer: "Add per-person subtotals to the receipt", not "added stuff".
  • Reference the issue in the subject or body (#14).
  • Use the body to explain why, not what. The diff shows what.
  • Mark AI-assisted commits with a Co-Authored-By: trailer for the tool you used.

PRs are squash-merged, so the PR title becomes the commit on main. Write PR titles to the same standard.

Review & approval controls on main

Enforced by a GitHub repository ruleset (Settings → Rules → Rulesets → main):

  • Changes only via pull request; no direct pushes.
  • 1 approving review from someone other than the author; new pushes dismiss stale approvals.
  • Required status checks: Lint, typecheck, unit tests, audit and End-to-end (Playwright) must pass, and the branch must be up to date with main.
  • No force-pushes, no deleting main.
  • Bypass: only the repository admin (Jordan), for emergencies. Every bypass is recorded in GitHub's rule insights.

Every PR uses the PR template: linked issue, how you tested it, and whether AI was used.

5Issue tracking Live board

All work is tracked as GitHub Issues on our GitHub Projects board, next to the code, so PRs link to issues automatically.

Columns (the Status field)

Backlog→To Do→In Progress→Blocked→Peer Review→Done
Column Means
Backlog Ideas and requests, ordered by the PO. Not yet ready.
To Do Ready (meets Definition of Ready), in the current sprint's Iteration
In Progress Someone's actively on it. Limit: 2 per person.
Blocked Waiting on someone or something. Say what in a comment and raise it at standup.
Peer Review PR open and waiting for review
Done Merged and deployed. Merging a PR with Closes #N closes the issue and moves it here automatically.

Fields & labels

  • Sprint (1-week Iteration field): which sprint the issue is in.
  • Estimate: story points.
  • Labels: feature, bug, chore, incident, good first issue.

Your first issue: filter the board by label:"good first issue", assign yourself, and bring it to Monday planning.

6AI agents & controls Rules file + enforced limits

AI makes a small team fast, and it also makes mistakes confidently. We use it heavily inside clear limits: agents propose, humans review and commit.

Approved tools

Tool Use it for Setup
Claude Code Planning, implementing, testing, debugging and reviewing: all agent roles below claude.com/claude-code (terminal, VS Code extension or desktop app); sign in with the team account
GitHub Copilot Inline autocomplete and quick chat in the editor VS Code extension; in your Copilot settings set Suggestions matching public code to Blocked

Anything else (ChatGPT, Cursor, other assistants) isn't approved for Settled code. Ask the tech lead if you want to propose a new tool.

The rules file

Every agent reads CLAUDE.md (Copilot reads .github/copilot-instructions.md, which points to the same rules). It covers the architecture, commands, conventions and guardrails. When a convention changes, update the rules file in the same PR.

Agent roles: right model for the job

Role When Model tier
Inspect & plan Start of every issue: read the issue and code, write a plan before any code Top (Claude Opus)
Implement Build the agreed plan Mid (Claude Sonnet) · Copilot inline
Test & verify Before every commit: run npm run check, add missing tests Mid / small (Sonnet, Haiku)
Bug diagnosis & fix Reproduce from logs or steps; write a failing test first Mid (Sonnet)
Code review & security Before opening a PR: run /code-review and /security-review in Claude Code Top (Claude Opus)

Guardrails

  1. You own every line. Read and understand all AI-written code before committing. "The AI wrote it" is never a review answer.
  2. Agents never commit, push, or change GitHub/Render settings. Enforced for Claude Code by the shared .claude/settings.json, which denies git commit, git push and reading or editing .env.
  3. No secrets or customer data in prompts. Never paste keys, .env contents, or real user data into any AI tool.
  4. Stripe test keys only, and the server refuses live keys by design.
  5. Don't weaken controls (lint rules, tests, CI, branch rules) to make AI output pass. Fix the code.
  6. Disclose it. Tick the AI-usage box in the PR template.

7Code quality Hook + CI + Security tab

Quality checks run three times: in your editor (on save), at commit (husky pre-commit hook), and in CI (required to merge).

Tool Config What it does
ESLint 10 eslint.config.js typescript-eslint recommended-type-checked (catches unhandled promises, unsafe any, …) + React Hooks rules + React Refresh; eslint-config-prettier last so formatting is left to Prettier
Prettier 3 .prettierrc.json All formatting (120-character lines). Never argue about style in review.
husky + lint-staged .husky/pre-commit, package.json On every commit: eslint --fix + prettier --write on staged files only
TypeScript tsconfig.json strict, noUncheckedIndexedAccess, no unused locals or params
GitHub Actions CI .github/workflows/ci.yml Lint, format check, typecheck, Vitest, npm audit, Playwright on every PR and push to main

Vulnerability scanning

Scanner Catches Where you see it
Dependabot (.github/dependabot.yml) Known-vulnerable dependencies; opens weekly grouped update PRs (Mondays) Security tab · PRs
CodeQL (default setup) Injection, XSS, unsafe data flows in our own code PR checks · Security tab
Secret scanning + push protection Blocks a push that contains a Stripe key or other credential Your git push is rejected with instructions
npm audit --audit-level=high High or critical advisories in the dependency tree Fails the CI job

Commands

npm run check        # everything CI checks except E2E: run before pushing
npm run lint:fix     # auto-fix lint issues
npm run format       # format the whole repo

Never disable a rule inline (// eslint-disable, @ts-ignore) without the tech lead's OK in the PR.

8Testing frameworks Runs in CI

Vitest for unit, integration and API tests; Playwright for end-to-end tests in real browsers. Both run on every PR and must pass to merge.

Type Tool Where Example in our code
Unit Vitest test/rules.test.ts Guests can't remove others' items; tax is 8.45% of the subtotal; prices come from the menu
Integration Vitest + real server + Socket.IO clients test/sync.test.ts 50 simultaneous adds from two clients: both end identical and see every version once, in order
API Vitest + fake Stripe gateway test/checkout.test.ts Order isn't placed until Stripe confirms; a wrong amount is rejected; cancel unlocks the cart
End-to-end Playwright (Chromium) e2e/group-order.spec.ts Two separate browsers create and join an order and see each other's items live

How testing fits the workflow

  • New cart behavior → a pure function in src/server/cart/rules.ts plus unit tests.
  • Anything users see change in real time → an integration test in the sync.test.ts style.
  • Bugs → write a failing test that reproduces it first, then fix.
  • New user flows → extend the Playwright spec.
  • Payments → tested against the fake gateway in CI. Real Stripe test-mode payments are checked by hand (card 4242 4242 4242 4242; decline: 4000 0000 0000 0002). 
npm test                  # Vitest: unit + integration + API (about 2 s)
npm run test:e2e          # Playwright: builds, starts the server, runs two browsers
npx playwright install chromium   # first time only

We define what to test; AI can help write the tests. You still review every assertion.

9Other controls, tools & infrastructure

Hosting, deploys, secrets, your day-1 checklist, and what to do when production breaks.

Infrastructure & hosting

What Where How it's created
App (React + API + Socket.IO) Render web service (free plan, Node 22, one instance) Scripted: render.yaml Blueprint (infrastructure as code)
Payments Stripe, test mode only Keys from the Stripe dashboard → Render environment variables
This playbook GitHub Pages The docs/ folder on main
Cart data Server memory Resets on restart, deploy or sleep (known MVP limitation)

Free Render services sleep after 15 idle minutes, so the first request afterward takes about a minute. Health check: /api/health.

Deploys & rollbacks

  1. Merging a PR to main triggers an automatic Render deploy (3–5 minutes).
  2. Watch it in Render → settled → Events. When it says Live, open the app and run a two-browser smoke test (create, join, add, see it sync).
  3. If an auto-deploy doesn't start, use Manual Deploy → Deploy latest commit.
  4. Rollback: Render → Events → pick the last good deploy → Rollback. Then fix forward with a normal PR (or git revert the bad merge).

Secrets

Secret Local dev Production
STRIPE_SECRET_KEY (sk_test_…) .env (git-ignored) Render → Environment
STRIPE_PUBLISHABLE_KEY (pk_test_…) .env Render → Environment (served to the browser by /api/config)
  • Never commit secrets. .env is git-ignored, and GitHub push protection blocks keys that slip through.
  • Test keys only. The server refuses to start payments with live keys.
  • Get keys from Jordan over a private channel, never in an issue, PR, commit or AI prompt.
  • If a key leaks: tell Jordan right away → Stripe dashboard → Developers → API keys → Roll key → update .env and Render → redeploy → file an incident issue.

On-call & incidents

One engineer is on call each week (Monday 9am to Monday 9am, rotation set at sprint planning), with Jordan as backup. On call means you watch for problems and respond within the times below during waking hours.

Severity Example Respond within
Sev 1 App down; carts not syncing; checkout broken for everyone 30 minutes; drop sprint work
Sev 2 A key feature broken for some users (e.g. QR join fails on iOS) 4 hours
Sev 3 Cosmetic or minor bug with a workaround Next sprint planning
  1. Confirm: reproduce it, check /api/health, Render logs, and the last deploy time.
  2. Mitigate first: if the last deploy caused it, roll back in Render. Diagnose after.
  3. Communicate: post status in the team channel when you start and when it's resolved.
  4. Write it up within 48 hours: an issue labeled incident covering what happened, impact, root cause, and the follow-up issues. Blameless.

Known limitations

Carts live in memory, the host role is tied to a browser, there's no bill splitting yet, and more. See the README's known-limitations list. Most of them are already on the board.
